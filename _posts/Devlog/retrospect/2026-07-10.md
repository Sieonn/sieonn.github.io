## 배운 점 / 인사이트

- **대규모 UI 재구현의 레이어 관리**: 캘린더 리스트뷰와 그리드 헤더 개선이 동시에 진행되면서, 각 컴포넌트가 미치는 영향 범위를 정확히 파악해야 회귀 버그를 줄일 수 있음을 배웠다. 한 군데의 높이·색상 변경이 연쇄적으로 다른 영역에 영향을 미친다.

- **스타일 토큰화의 실전 가치**: 색상·크기를 하드코딩에서 토큰으로 전환하면서, 후속 수정이 훨씬 단순하고 일관성 있게 변한다. UI 가이드 변경 시 한 곳만 수정하면 전체에 반영되는 경험.

- **그리드 렌더링 복잡도의 정점**: 병합 행, 조건부서식, 필터 인디케이터, 그룹 요약 행이 모두 활성화된 상태에서는 렌더링 순서와 CSS 우선순위가 예측 불가능해진다. 계층화(z-index)와 명확한 책임 분리가 필수.

- **Cypress 선택자의 안정성 중요성**: 79개 커밋에서 HTML 구조가 빈번히 바뀌면서 testid 기반 선택자도 깨질 수 있다. e2e 테스트가 신뢰할 수 없어지면 회귀 검증 비용이 급증한다.

- **기능 단위보다 계층 단위 커밋의 필요성**: 같은 기능이라도 "디자인 모드 헤더"와 "사용 모드 헤더"를 분리하거나, "컴포넌트 구조 변경"과 "스타일 적용"을 분리하면 리뷰와 추적이 훨씬 명확해진다.

## 어려웠던 점 / 막힌 부분

- **79개 커밋의 규모 관리**: 대규모 변경사항을 한 번에 푸시하면서 각 커밋의 목적과 부작용을 추적하기 어려웠다. 특히 중간에 버그를 발견하면 어느 커밋부터 회귀했는지 binary search가 필요함.

- **캘린더 리스트뷰 재구현의 복잡도**: 날짜 표시 로직과 이벤트 렌더링 타이밍이 얽혀있어서, 한쪽을 수정하면 다른 쪽이 깨지는 패턴이 반복됨. 근본 구조가 안정화될 때까지 예측 불가능한 상태.

- **GridCell/GridLayer 의존성**: 그리드 셀의 높이가 바뀌면 레이어 마스킹도 다시 계산해야 하는데, 두 컴포넌트가 강하게 결합되어 있어서 수정이 카스케이딩됨.

- **스타일 우선순위 충돌**: 조건부서식 커스텀 배경색, 짝수행 교번색, 호버 배경색이 모두 동시에 활성화되면 어느 것이 우선할지 불명확. CSS 우선순위 계산이 복잡해짐.

- **Cypress 테스트의 신뢰도 하락**: HTML 구조가 자주 바뀌면서 기존 testid가 더 이상 유효하지 않은 경우가 발생. 테스트가 깨졌는데 기능은 정상인 경우를 구분하기 어려움.

- **encke-grid 빌드 동기화**: 외부 라이브러리 빌드 결과를 커밋에 포함시키면서, 빌드 타임스탬프로 인한 불필요한 변경으로 diff가 오염됨.
