## 💡 배운 점 / 인사이트

- **데이터 폭 불일치 방어**  
  데이터 배열이 헤더 정의와 항상 일치한다고 가정하면 안 된다. foreign column 응답에서 비표준 폭을 받을 수 있고, 이는 index 기반 접근을 unsafe하게 만든다.

- **순수 함수로 리팩터한 뒤 테스트 작성이 정말 편함**  
  SplitView.tsx render()는 DOM 생성과 상태 읽기가 섞여 있어서 직접 테스트하기 어렵다. 계산 로직을 SplitView.layout.ts로 분리하자마자 캐릭터라이제이션 테스트 33개를 깔끔하게 작성할 수 있었다. 이후 render() 수정 시 테스트만 보고 신뢰도 높게 리팩터 가능.

- **조건식 폭발과 단계별 판정의 차이**  
  collapse bar의 merge/title 노출은 "frame tree 깊이, split 방향, 형제 상태"를 동시에 봐야 한다. 이를 13단계의 else-if 사다리로 나열했을 때보다, 순수 함수로 "어떤 조건이 true면 이것을 사용하겠다"는 의도를 먼저 명시하고 구현하는 게 훨씬 읽기 좋다.

- **Form 컴포넌트는 GridManager 수정이 자동 전파됨**  
  Form들은 RECORDS를 직접 인덱싱하지 않고 sourceGrid.columnMap을 공유 참조하므로, GridManager에서의 foreign column 방어 로직이 자동으로 Form에도 적용된다.

## 🧱 어려웠던 점 / 막힌 부분

- **collapse bar의 render() 사다리 이해**  
  초반에는 flex/size 계산 13단계와 merge-bar/title 판정이 얽혀 있어서 어느 단계까지가 "무조건 실행"이고 어디부터 "조건부"인지 헷갈렸다. 함수 시그니처를 정의하면서 입력값(frame, parent 상태)과 출력값(flex/size/render flag)을 명확히 분리하자 한 번에 정리됨.

- **형제 프레임 탐색 중복의 숨은 조건**  
  3곳에서 "형제를 찾는" 로직이 있는데, 각각이 약간 다른 상황(collapsed 그룹 찾기, merge bar 판정, size 계산)에서 쓰였다. getSiblingFrame으로 통합하면서 "split parent 기준으로 형제를 정의한다"는 가정이 모든 곳에서 일관되는지 검증하는 데 신경 썼다.

- **foreign column 데이터 폭 버그의 upstream 원인**  
  왜 RECORDS 행이 COLUMN HEADER 폭과 다를 수 있는가? (처음엔 백엔드 버그 의심) 조사 결과, getValuesByColumnId가 이미 쿼리 결과를 정규화하는데, postDataGetForeignColumnsData는 그 결과를 raw로 받아서이다. 근본적으로는 정규화 책임을 더 상위에서 잡아야 하지만, 현재로서는 방어 로직으로 충분함.
